# Stage 5.5 OCFL resource storage

The active `0.0.0-stage5.5` reactor replaces completed-file placement with OCFL beneath Deposit resource management. Acceptance is recorded in the [hub status](../../deposit-hub/implementation_status.md) and external `stage5.5-checkpoint.json`; this implementation description does not itself establish acceptance. Stage 4 and Stage 5 source snapshots, fingerprints, checkpoints and reports describe the accepted original file backend and remain historical evidence.

`ResourceService` and `ResourceTransferRepository` retain authorization, transfers and receipts. `ResourceRepository` retains references, transaction-lifetime resource protection, leases and orphan eligibility. They use `ResourceStorage.Content` and streaming handles. `OcflResourceStorage` alone interprets physical paths, inventories and library types. `ResourceFiles` supplies naming/checksum validation and Deposit staging; `StorageManager` reconciles publication, removes committed staging copies, discovers private cleanup candidates and executes durable prune intents. `HistoryRepository` verifies retained content through the abstraction. `CoreRepository` maintains reference/orphan state without relocation. `ServerContext`, `DepositExtension` and `RuntimeReadiness` own startup, readiness and shutdown; transient history expiry still precedes resource recovery.

One canonical resource UUID is one exact OCFL object ID. Its only initial version is `v1`, with one payload named by the existing `storedFilename` algorithm. Identical uploads receive distinct objects. Changed bytes require a new Deposit resource ID. OCFL versions do not represent Deposit revisions, permissions, attachment state or retention. OCFL inventories contain no mutable Deposit lifecycle metadata.

The profile pins [OCFL 1.1 with 1.1.1 clarifications](https://ocfl.io/news/) (declarations remain `1.1`) and [ocfl-java 2.2.3](https://github.com/OCFL/ocfl-java/releases/tag/v2.2.3). Content/inventory digests use SHA-256. Extension [0004](https://ocfl.github.io/extensions/0004-hashed-n-tuple-storage-layout.html) uses SHA-256, three three-character tuples, and the full hash directory. The adapter disables the inventory cache and verifies staging, inventory structure, profile, payload size and fixity. Reads are bounded streams; the current public chunk API remains bounded to 4 MiB. The adapter verifies complete fixity before returning even an EOF/empty range. Public transport/DTO/error contracts remain unchanged and `downloadUrl` stays null until Stage 10.

`resourceRoot` is a writable Deposit container with sibling `ocfl/`, `staging/` and `ocfl-work/`. `exportRoot` is separate. Paths must be canonical, unlinked, outside database/transaction-log directories, and disjoint. OCFL and its work directory share a volume, as required by the [library usage guide](https://github.com/OCFL/ocfl-java/blob/v2.2.3/docs/USAGE.md). Exclusive root ownership prevents concurrent installations from publishing into the same root. Existing `live/`, `deleted/` or graph path/suffix records fail explicitly. There is no converter, compatibility backend or online migration: archive the stopped, test-owned installation with the existing guarded Reset phase, then recreate its graph/resource fixtures.

Publication copies staged content through `ocfl-java` while the Deposit resource lock is held through graph completion. A matching existing object is verified and reused; an invalid object fails explicitly. Neither retries nor graph rollback create `v2` or delete a published object. Ready metadata and the finish receipt commit after publication and verification. Maintenance then deletes the retained staging copy. Startup truncates uncommitted staged tails, verifies published content, reconciles pending deletion intents before discovery and clears exclusively owned library scratch. Upload sources remain outside that scratch directory.

Discovery inspects whole objects and separately checks incomplete/misplaced installations. Unknown valid objects get private cleanup records with their exact IDs, unknown Namespace sentinel and a new conservative orphan timestamp; no public DResource, permission or domain identity is reconstructed. Inventory files are never individual orphan candidates. Incomplete staging is tracked separately.

Only Deposit decides permanent pruning. A committed intent records the original sum of regular-file byte lengths (object inventory/sidecars/payload plus any remaining staged copy). The worker rechecks protections and orphan age under the existing lock, calls library `purgeObject`, confirms whole-object removal, then commits completion and the reclaimed count once. An interrupted partial purge resumes from the recorded intent; retries do not double-count. Scheduled/eligible counts retain their payload-based public meaning.

`runtime/ocfl-runtime-lock.json` records 16 effective dependencies, Maven artifact hashes, license evidence and provided-runtime mappings; nine additional JARs ship. Jackson, Caffeine and SLF4J use the pinned Neo4j versions, with matching hashes checked rather than shipping duplicate copies. The packaging audit includes OCFL/support classes as well as Neo4j/JTS. The pinned APOC and Neo4j stack already contains 55 byte-identical SLF4J definitions; the expanded audit records their hashes and permits only that exact baseline pair. New or differing duplicates block acceptance. Normal distributions omit the fault probe and its permissions.

Run `scripts/Invoke-Stage55Gate.ps1 -RunPrefix <fresh-id> -Port 17770`. It requires accepted Stage 0–5 checkpoints and verifies that none change. It runs cumulative normal/probe geometry, resource and history scenarios, then the real CLI interruption/resumption fixture. Historical placement assertions now inspect the identity-derived OCFL object and fixed `v1`; `relocation-before/after` crash cases are superseded by `staging-cleanup-before/after`. `collection-partial` deliberately removes one inventory file in a test-only backend wrapper under a committed deletion intent, then terminates the actual JVM; production restart uses library whole-object purge. The out-of-space case injects a filesystem exception at the storage boundary; it does not fill the host disk. Both controls exist only in the probe JAR.

`Test-OcflBackup.py` is the offline acceptance drill, not a scheduled backup service. It requires the stopped, owned installation and captures both databases and transaction logs, the complete OCFL/staging/work container, temporary exports, configuration and runtime manifests. It records every file's hash, independently validates the fixed OCFL profile/fixity, rejects corrupt/incomplete archives, archives the previous stopped state before replacement, and restores only to the same guarded installation. The gate deliberately changes graph/upload state after backup, restores it, then proves old sessions are invalid, upload receipts resume at the saved offset, and history-only bytes/protections survive. OCFL content alone cannot restore Deposit semantics. Stage 11 still owns scheduled/release backup acceptance; Stages 7–10 still own exchange, imports, formats and browser transport.

Stage 6 may start only after Stage 5.5's accepted checkpoint. No later-dependent acceptance ID is claimed complete by this refactor.
