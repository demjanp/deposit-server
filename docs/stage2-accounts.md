# Stage 2 accounts and session scope

Build identity: `0.0.0-stage2`. Runtime and third-party versions remain pinned to the accepted foundation. Acceptance is pending until the Stage 2 gate completes; see the hub status for actual evidence.

## Contracts and implementation

The API/service/repository boundaries and injected transaction remain unchanged. Account updates, password changes, administrative mode, Namespace metadata edits and whole-Namespace deletion use the documented request/result catalog. At least one enabled administrator and one enabled owner per retained Namespace survive all account/role updates. Identical passwords preserve hash, audit, sessions and revision; durable receipts record the no-op. Password receipt replay authenticates the caller but does not repeat old-password verification or revocation.

An edition-specific authorization adapter resolves ordinary roles and effective administrative owner access. A transaction-owned shared/exclusive authorization guard precedes actor/server/Namespace locks. Ordinary calls and login hold shared authorization leases until transaction completion; account changes, role changes and deletion hold exclusive leases. Concurrent independent domain writes remain possible; authorization changes wait for in-flight protected work. A read-to-authorization-write upgrade drops its read lease before waiting and reauthenticates, and is prohibited after a mutation. Server locks precede Namespace locks whenever both are needed. This coarse authorization fence is a deliberate scaling tradeoff, including for long read transactions.

The pinned lifecycle adapter registers a before-commit transaction listener for session expiry/current enabled-account/administrator checks, in addition to Stage 1 completion monitoring. Deliberately authorized self-demotion/disable is recognized within the single allowed mutation. Completion publishes revisions, token revocation, mode changes and deletion selection clearing before releasing guards; rollback publishes none of these. Password/disable revocation is centralized for later browser-session integration. Mode is captured with Namespace scope; explicit mode changes remain session controls, not domain actions.

Namespace discovery signs a fingerprint of complete filtered ordered portable results and the effective mode, in addition to actor/request/server-run/revision. It rechecks both throughout native streaming and before returning pages. Namespace-scoped mutations therefore invalidate affected discovery cursors without incrementing the server counter. Current implementation retains Stage 1 in-memory ordering; fingerprint revalidation is intentionally conservative and may be expensive for large discovery streams.

Deletion receipts use server scope and include the original target UUID and both preconditions in their keyed request identity. Completed deletion lookup/replay precedes live selection and revision checks. Receipts and operation bindings survive deletion; implemented domain nodes, role edges and identity registries do not. The originating enabled actor or a current administrator can recover a deletion, including while unselected or selecting another Namespace. Receipt data remains portable and the server revision in metadata is current.
